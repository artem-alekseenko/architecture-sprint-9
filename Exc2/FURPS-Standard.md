
| Код | Требования                         | Комментарий  |  
|-----|------------------------------------|--------------|  
| F   | Функциональные (Functionality)     |              |  
|  F1   | **Отображение доступных депозитов** (с актуальными ставками) на сайте и в интернет-банке.                    |На сайте для новых клиентов отображаются общие актуальные ставки. В интернет-банке для действующих клиентов дополнительно показываются персонализированные ставки (учёт лояльности, сумм на счетах и т. п.).Источник ставок: раньше XLS-файл, предполагается хранить ставки и логику расчёта в АБС (или отдельном сервисе).              |  
|   F2  | **Подача заявки на депозит**: На сайте – заполнение ФИО и телефона.  В интернет-банке – выбор счёта, суммы, подтверждение СМС-кодом.                               |        Сайт передаёт заявку в систему кол-центра, после чего оператор перезванивает клиенту. Интернет-банк передаёт заявку напрямую в банк (в АБС или промежуточный сервис) — нежелательно вызывать АБС напрямую; возможно, потребуется отдельный сервис. При передаче данных требуется шифрование (SSL/TLS).    |  
|  F3   |**Обработка заявки менеджером бэк-офиса** (MVP).                               |  Менеджер подтверждает условия депозита в АБС. При подтверждении клиенту уходит СМС с результатом. Затем в АБС формируется (или активируется) депозитный счёт.           | 
|    F4 | **СМС-уведомления при подтверждении ставки и открытии депозита**.                                | СМС-отправка через существующий СМС-шлюз. Требуется минимизировать доработки в существующем «ядре» интернет-банка, по возможности реализовать логику силами команды банка.         |
|    F5 | **Возможность расчёта и ведения «специальных ставок»** для клиента.                                |     Сейчас «спецставки» считаются вручную (XLS + согласование с кредитным бэк-офисом). Нужно организовать хранение и механизм расчёта спецставок (скорее всего, в АБС или в едином справочнике).         | 
|    F6 | **Управление безопасной передачей данных** (SSL/TLS) для всех форм подачи заявки.                                |       На сайте — шифрование https. При интеграции интернет-банка с новой сервисной шиной (или API) – также шифрование.        |
| U   | Удобство использования (Usability) |              |  
|   U1  | **Интерфейс, соответствующий принятой системе дизайна** (брендинг, фирменные цвета, единый UX).                                |  Единое оформление и понятные формы (как на сайте, так и в интернет-банке). Все элементы (кнопки, поля ввода, шрифты) должны соответствовать дизайн-системе банка.           |  
|     U2| **Высокая скорость отклика и простота взаимодействия** (MVP-сайт и интернет-банк).                               |        Пользователи не должны ждать более 1-2 секунд при загрузке информации. В идеале - до 500 миллисекунд.      |  
|     U3| **Удобство взаимодействия с кол-центром** для новых клиентов.                                |   Оператор видит заявку, быстро предлагает «спецусловия», если применимо.           |  
| R   | Надёжность (Reliability)           |              |  
|     R1| **Доступность 99,9%** в режиме 24/7 для ключевых сервисов (интернет-банк, сайт) при поддержке в случае переключения на резервный ЦОД.                               | Необходимо учесть отказоустойчивую архитектуру.             |  
|     R2| **Гарантия целостности данных** в процессе передачи заявок (сайт → кол-центр → АБС, интернет-банк → АБС).                                | Исключить потерю заявок при сбоях (нужно продумать надежные механизмы очередей, транзакций и т. п.).             |  
|     R3| **Безопасность персональных данных** (ФИО, телефон, индивидуальные ставки).                                |   Данные шифруются при передаче (SSL/TLS). Возможный дополнительный контроль доступа (роли «оператор кол-центра», «бэк-офис депозитов» и т. д.).           |  
| P   | Производительность (Performance)   |              |  
|     P1| **Время отклика < 1 сек** при загрузке списка депозитов и справочных данных.                                |     Сейчас отмечено, что некоторые справки грузятся >1 сек. Надо оптимизировать.         |  
|     P2| **Горизонтальное масштабирование** (в идеале) для интернет-банка и новой сервисной шины/приложения.                                | АБС масштабируется только вертикально из-за специфики Oracle/PL/SQL. Новый сервис, обеспечивающий подачу заявок, желательно строить «без узких мест», чтобы он мог выдерживать рост клиентской базы.             |  
| S   | Поддерживаемость (Supportability)  |              |  
|     S1| **Использовать уже существующие технологии** (MS SQL, Oracle, Java, .NET) там, где это возможно.                                |  Избежать сложных новых продуктов, где нет компетенций у команды.            |  
|     S2| **Подготовка документации** (архитектурной, пользовательской, администрирования) для дальнейшего расширения.                                | Необходима детализация API, схемы БД, механизмы деплоя, оповещения и т. д.            |  
|     S3| **Возможность эволюционного перехода к микросервисной архитектуре интернет-банка** (хотя бы частично для открытия депозитов).                                |  Пока IB – монолит (ASP.NET MVC), нужно продумать отдельный модуль/сервис для депозитов.            |  
| +R  | + Ограничения (Restricitions)      |              |  
|     R1| **Запрет прямого API-взаимодействия интернет-банка с АБС** в новом процессе открытия депозитов (по требованию надёжности и масштабирования).                                | АБС перегружена, прямые запросы могут поставить под угрозу работоспособность банка.             |  
|     R2| **Необходимость очной идентификации** для новых клиентов.                                |     Требование законодательства: по телефону или онлайн нельзя полностью открыть вклад без визита в отделение.         |
|     R3| **Использование резервного ЦОД** при сбоях.                                |   Желательно обеспечить «горячее» или «полугорячее» переключение.           |
|     R4|**Ограничения на изменения ядра СМС-системы** (сторонний подрядчик).                                |   Предпочтительно дорабатывать логику отправки СМС «со стороны банка».           |
