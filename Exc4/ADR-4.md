Технологически необходимо, чтобы **АБС или промежуточный сервис** умели забирать эти данные и предоставлять (или формировать) актуальную «выгрузку» для кол-центров.    |

Если по клиенту требуется специальная ставка, бэк-офис согласовывает её (по старому процессу) и оперативно обновляет запись. <br>2. Кол-центр банка сразу видит обновлённую ставку, а партнёрский кол-центр получит изменение в следующем файле выгрузки.                                              |

## 2. Нефункциональные требования

| **№** | **Требование**                                                                                                                                                                                                                                                                        |
|:----:|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1    | **Безопасная передача файла** для партнёрского кол-центра (например, шифрованный файл, защищённый канал SFTP)                                                                                                                                                                          |
| 2    | **Минимальная задержка** обновления ставок в кол-центре (банка). Операторы должны видеть актуальные данные фактически в реальном времени.                                                                                                                                             |
| 3    | **Небольшая задержка** допустима для партнёрского кол-центра. Там могут выгружаться файлы, например, каждый час или каждые 4 часа.                                                                                                                                                     |
| 4    | **Использовать имеющиеся инструменты** (XLS/CSV, почтовые сервисы/FTP, оракловая БД АБС, SQL) без существенного изменения архитектуры интернет-банка.                                                                                                                                 |
| 5    | **Надёжность**: выгрузка для партнёрского кол-центра не должна «ломать» основную АБС. Желательно, чтобы механизмы выгрузки/генерации файла работали с копией данных, чтобы не перегружать основное ядро.                                                                               |
| 6    | **Совместимость**: новые изменения должны вписываться в общую концепцию MVP (онлайн открытие депозитов), не внося критических задержек или конфликтов.                                                                                                                                 |

## 3. Решение

См. диаграммы.

**Логика**:
1. **Обновление ставок**: Бэк-офис заполняет Excel → загружает данные в таблицу Oracle (AБС).
2. **Call Center System (банка)**: при открытии экрана оператором → запрос «Get Current Rates» → (внутри) Java-приложение лезет за свежими ставками (либо кэшированно, либо напрямую).
3. **Rate Exporter**: раз в час → SELECT из Oracle «DepositRates» → генерирует файл → SFTP → **Partner Call Center**.

Таким образом **не перегружается** АБС: выгрузка может идти из копии таблицы или в ночное/почасовое окно.

## 4. Альтернативы
1. **API для партнёрского кол-центра**
    - Партнёр не готов к прямому API, у них нет механизма интеграции — они хотят именно файл.
2. **Отправка Excel-файлов по почте**
    - Менее надёжно, возможны человеческие ошибки и задержки. Требует ручной рассылки.
3. **Прямой экспорт из Excel** (бэк-офис: «нажал кнопку, отправил»)
    - Нежелательно, т. к. привязывает процесс к действиям человека. Мы хотим автоматическую выгрузку.

### Недостатки, ограничения, риски
- **Дублирование данных** (Excel → АБС → выгрузка → партнёрская система) может привести к несоответствию, если кто-то забудет вовремя обновить.
- **Безопасность** передачи файлов — нужно убедиться, что доступ к файлам есть только у партнёрского кол-центра (SFTP, VPN или другие меры).
- **Старая база Oracle** (АБС) может быть перегружена, если делать слишком частый экспорт. Нужно ограничить периодичность выгрузки или работать через копию / реплику.
- **Зависимость от компетенций**: может потребоваться писатель PL/SQL-скриптов или Java, умеющий работать с SFTP, если выбрано решение реализовать Rate Exporter как Java-приложение.

## 5. Список крупных задач (для будущего планирования)
Ниже — **список ключевых задач** по системам:

1. **АБС / Бэк-офис**
    - Доработать схему хранения ставок (таблица, процедура загрузки из Excel).
    - Создать процедуру/функцию для запроса актуальных ставок (если нужно).
    - (Опционально) Настроить репликацию таблицы «DepositRates» в отдельный schema/DB, чтобы не нагружать основную.

2. **Система кол-центра (банка)**
    - Реализовать API/метод «getDepositRates()» (либо прямой доступ к таблице, если архитектурно допустимо).
    - Добавить в UI (React) вкладку/раздел «Актуальные депозиты» для оператора.

3. **Rate Exporter (новый модуль)**
    - Написать скрипт/сервис, который обращается к таблице «DepositRates».
    - Формировать XLS/CSV.
    - Передавать файл на SFTP-сервер/папку для партнёрского кол-центра, с учётом шифрования/защиты.

4. **Партнёрский кол-центр**
    - Настроить приём файлов (SFTP, расписание).
    - Автоматическая или полуавтоматическая загрузка их в собственную систему, чтобы операторы видели актуальные ставки.

5. **Интернет-банк, Сайт**
    - (Могут не требовать доработки в рамках этой конкретной задачи, так как сейчас речь идёт лишь о предоставлении ставок в кол-центры.)

## 6. Общий RoadMap (6 месяцев и горизонт 1 года)

1. **Месяц 1**:
    - Анализ и согласование формата выгрузки (XLS/CSV), протокола передачи (SFTP).
    - Подготовка схемы таблицы «DepositRates» в АБС (или дополнительной DB).
2. **Месяц 2**:
    - Реализация сохранения ставок в АБС (загрузка из Excel).
    - Начальная интеграция Система кол-центра ↔ АБС для получения ставок.
3. **Месяц 3**:
    - Разработка модуля Rate Exporter (скрипт/сервис).
    - Тестовая выгрузка и передача файла партнёрскому кол-центру.
4. **Месяц 4-5**:
    - Тестирование полного контура, выявление узких мест.
    - Обучение операторов, обновление скриптов звонков.
    - Резервный план и безопасность (SFTP, доступы, мониторинг).
5. **Месяц 6**:
    - Запуск в промышленную эксплуатацию с партнёрским кол-центром.
    - Снятие метрик (насколько увеличился поток звонков).

**Горизонт 1 года**

Через год предполагается:

- Полная автоматизация процесса открытия депозитов онлайн (без ручного согласования бэк-офисом).
- Расширение микросервисной архитектуры (особенно для интернет-банка и Rate Exporter).
- Возможность API-интеграции с партнёрскими кол-центрами (если они обновят ПО), уход от ежечасных файлов.
- Устойчивое масштабирование — резервный ЦОД полноценно задействован для всех ключевых систем.
- Единая система расчёта ставок (возможно, без Excel), которая синхронизирована с кредитным и депозитным подразделениями.
